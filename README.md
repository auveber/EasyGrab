# EasyGrab (beta 0.4) — собираются все три соцсети

Схема версий проекта: **pre-alpha** — готов только интерфейс; **alpha** —
по-настоящему собирается хотя бы одна из трёх соцсетей; **beta** — все три,
но с доработками; **release** — законченный проект.

Сейчас **beta**: по-настоящему собираются все три — YouTube (официальный
Data API v3), TikTok (yt-dlp) и Instagram (instaloader). Заглушек в приложении
не осталось.

| Площадка | Чем собирается | Нужен вход? |
|---|---|---|
| YouTube | Data API v3 | нет, только API-ключ |
| TikTok | yt-dlp | **нет**, анонимно |
| **Instagram (experimental)** | instagrapi | **да**, логин и пароль бёрнера |

Порядок площадок везде один: **YouTube → TikTok → Instagram**. Он задан одной
строкой `PLATFORMS` в `app_state.py` и оттуда расходится на вкладки окна входа,
кружки статуса, колонки таблицы, строки итогового окна и все выгрузки.
Instagram стоит третьим намеренно: он самый нестабильный, и глаз должен
натыкаться сначала на то, что работает предсказуемо. В интерфейсе он помечен
как `(exp.)`, а перед сбором с его участием всплывает окно с предупреждением
и галочкой «больше не спрашивать».

## Как собирается YouTube

Только API-ключ, без OAuth и без входа в Google-аккаунт — берутся
исключительно публичные данные. Это важно для изоляции рабочих аккаунтов:
приложение не знает ни одного логина Google и не может связать каналы
между собой.

Поток на один канал (`backend_youtube.py`):

1. `channels.list` по ссылке канала → ID канала, подписчики, накопительные
   просмотры канала и `uploadsPlaylistId` (плейлист «Загрузки»);
2. `playlistItems.list` постранично по этому плейлисту → ID роликов;
3. `videos.list` с `part=statistics`, батчами до 50 ID за вызов →
   `viewCount` / `likeCount` / `commentCount` каждого ролика;
4. суммирование в одну тройку чисел на канал.

**Расход квоты.** У проекта в Google Cloud 10 000 юнитов в сутки, каждый из
этих вызовов стоит 1 юнит. На замере по 20 реальным каналам ушло **59 юнитов
(0,6 % суточной квоты) за 29 секунд**. То есть сбор можно спокойно запускать
десятки раз в день.

**Что показывается в колонке «Просмотры».** По умолчанию — сумма просмотров
по роликам канала: тогда просмотры, лайки и комментарии посчитаны по одному
и тому же набору роликов и сходятся между собой. Если нужно ровно то число,
что стоит в вашей таблице «Продакшн» в колонке «Накопительное кол-во
просмотров», поменяйте в начале `backend_youtube.py` одну строку:

```python
YT_VIEWS_SOURCE = "channel"     # было "videos"
```

Разница обычно небольшая (у канала «Trapped Underwater» — 16 против 14):
счётчик канала включает удалённые и скрытые ролики, а сумма по роликам — нет.

## Как собирается TikTok

Официального публичного API, сравнимого с YouTube Data API, у TikTok нет:
их Display API требует одобрения приложения и OAuth-входа во **все** рабочие
аккаунты — это связало бы 20 аккаунтов в одну систему. Поэтому публичные
данные берутся через **yt-dlp**.

**Вход не нужен вообще, и это проверено по коду.** В экстракторе TikTok внутри
yt-dlp слова `username`, `password` и `_perform_login` не встречаются **ни разу**,
а `cookies` — 12 раз. То есть логин с паролем он физически не умеет принимать,
и поле для них ни на что бы не влияло.

Довод важнее технического: привязывать учётку TikTok **вредно для изоляции**.
Если один вьюер-аккаунт каждый день заходит ровно на ваши 19 профилей, он сам
становится ниточкой, по которой их связывают между собой — тот самый признак
связанных аккаунтов, из-за которого и прилетает теневой бан. Анонимный запрос
не несёт никакой личности, связывать нечего.

Поэтому вкладка TikTok в окне входа не содержит полей — там объяснение
и значок ⓘ с разбором, что такое аккаунт-бёрнер и как работает антифрод.
Кружок «TT» в статус-баре горит сразу при запуске. Если TikTok когда-нибудь
начнёт требовать проверку, понадобится файл cookies — и это тоже будет
отдельный одноразовый бёрнер, а не один из ваших двадцати.

## Обновление yt-dlp

Тихого автообновления в приложении **нет намеренно**. Вы сравниваете цифры
день ко дню: если движок сбора молча сменит версию и числа поедут, будет
не отличить просадку каналов от смены версии. К тому же новая версия ломается
не реже, чем чинит.

Вместо этого приложение при запуске в фоне сверяет установленную версию
с последней стабильной на PyPI. Если вышла новее — показывает окно с двумя
кнопками: **«Пропустить»** (работаем на текущей) и **«Обновить»** (ставит новую
и сразу на ней работает). Перезапуск не нужен: yt-dlp вызывается отдельным
процессом, поэтому следующий же сбор берёт обновлённую версию.

Спрашивает при **старте приложения** и только там — открытие других окон
вопрос не повторяет. Обновление не требует перезапуска: yt-dlp вызывается
отдельным процессом, поэтому следующий же сбор возьмёт новую версию.

Установленная версия видна в окне **«О программе»** (клик по названию
«EasyGrab» в шапке) со значком ⓘ, где всё это и написано. Даты рядом
с версией нет намеренно: у yt-dlp **номер версии и есть дата сборки**,
`2026.07.04` — это 4 июля 2026, и печатать её дважды незачем.

## Версия и дата считаются сами

Раньше и версия, и дата были константами в `app_state.py`. Дата отстала
на пять дней, потому что про неё забывали — и забывали бы всегда.

Теперь ручной остаётся только **стадия** (`APP_PHASE = "beta"`): это решение
о зрелости продукта, его из файлов не вычислить. Номер сборки и дата считает
`build_info.py`:

- при запуске снимается отпечаток исходников — хэш содержимого всех `.py`;
- отличается от сохранённого → код менялся: номер сборки +1, дата сегодняшняя;
- не отличается → версия и дата стоят на месте, сколько бы раз ни запускали.

Хэш содержимого, а не время изменения файлов: время сбивается от любого
копирования папки, а интересуют настоящие правки. Всё хранится в `build.json`
рядом с приложением; если записать не удалось (папка только для чтения) —
версия просто не растёт, ничего не ломается.

Ссылка на GitHub задаётся одной строкой в `app_state.py`:

```python
GITHUB_URL = "https://github.com/ваш-аккаунт/easygrab"
```

Пока она пустая, окно честно пишет «ссылка появится позже» и ничего
не открывает.

Отдельно приложение распознаёт в ошибках признак того, что TikTok поменял
свою страницу и разборщик отстал, и прямо пишет: «скорее всего yt-dlp устарел,
обновите».

**Один запрос на профиль.** При `--flat-playlist` TikTok отдаёт
`view_count` / `like_count` / `comment_count` **прямо в списке роликов**.
Это ключевое отличие от прежнего решения, где на каждый ролик запускался
отдельный процесс yt-dlp: на профиль в 21 ролик там был 21 запуск вместо
одного. Замер на 19 реальных профилях: **47 секунд, все 19 собрались,
без cookies**.

yt-dlp запускается как модуль текущего интерпретатора
(`sys.executable -m yt_dlp`), а не как команда из PATH — так он находится
всегда, если установлен в то же окружение, что и приложение. Отдельным
процессом, а не библиотекой — ради жёсткого таймаута: зависший разбор
не подвесит приложение.

**Нулевые просмотры при живых лайках.** Если у профиля все ролики показывают
0 просмотров, но лайки есть, приложение пишет предупреждение в тех.журнал:
лайк ставит тот, кто посмотрел, значит TikTok скрыл счётчик показов — типичный
признак теневого бана. Сбор при этом не проваливается, лайки и комментарии
настоящие.

## Почему в приросте иногда бывает «−1»

Счётчики просмотров у YouTube **не мгновенно согласованы между серверами**.
Это проверено прямым замером: один и тот же ролик за 40 секунд показал
10 → 27 просмотров, а сумма по каналу вернулась с 2801 обратно на 2818.
Соседние запросы попадают на разные реплики и отдают то более свежее,
то более старое значение.

То есть маленький минус в приросте — это шум измерения, а не спад. Ничего
не теряется. Отличить от настоящей потери просто: при удалении ролика упало
бы и число роликов (`videos_counted` в тех.журнале), и падение было бы
заметным, а не в единицы.

Прятать такие минусы приложение не будет: показывать правду полезнее,
чем подчищенную картинку.

## Как собирается Instagram

Единственная из трёх площадок, где **вход обязателен**. Это не выбор, а
ограничение Instagram — проверено прямыми запросами:

- instaloader без входа → `429 Too Many Requests` на первом же обращении;
- yt-dlp без входа → «Instagram sent an empty media response… use --cookies».

Анонимного пути в 2026 году просто нет. Поэтому нужен **отдельный
аккаунт-бёрнер**: заводится только для просмотра, не входит в двадцать рабочих
и ни с одним из них не связан.

**Пароль не нужен вообще — сессия берётся из браузера.** Вы входите под
бёрнером в Safari или Chrome обычным человеческим образом, а приложение
забирает оттуда готовую сессию (кружок «IG» → выбрать браузер → «Взять
сессию»). Программного входа при этом не происходит **ни разу**, а он для
Instagram самое заметное событие. Побочный плюс: пароль не попадает ни в поля
приложения, ни в `session.json`.

**Нужный профиль браузера находится сам.** У человека обычно несколько профилей
Chrome (личный, рабочий), и вход в Instagram может быть в любом — а библиотека
по умолчанию читает только «Default». На живом Mac сессия оказалась в «Profile 4»,
и импорт молча её не находил. Теперь приложение перебирает профили и берёт тот,
где действительно есть ключ сессии. При этом читаются только имена ключей из
копии файла: значения cookie не трогаются, а оригинал не открывается — браузер
держит его занятым.

Поддерживаются Safari, Chrome, Firefox, Edge, Brave, Opera, Vivaldi, Chromium.
На macOS у **Safari** cookie закрыты системой: проще войти под бёрнером
в Chrome, чем выдавать Терминалу полный доступ к диску. Приложение так
и подсказывает.
Если сессию прочитать не вышло, приложение говорит почему: браузер не найден,
в нём нет входа в Instagram, файл занят открытым браузером или macOS не дала
доступ к диску.

## Instagram нестабилен — и это надо знать заранее

YouTube и TikTok собираются ровно и предсказуемо. Instagram — нет, и разница
не в качестве кода, а в устройстве площадки: открытого доступа к данным у неё
нет, любой сбор идёт через вход под аккаунтом, а автоматизацию она активно
ищет и ограничивает.

Как это выглядит на практике — по итогам живой проверки:

| Что делали | Чем кончилось |
|---|---|
| Сбор с добором просмотров по каждому ролику (8 запросов на профиль) | предупреждение «заподозрили автоматизированные действия» на первом же сборе |
| Сбор без просмотров (1 запрос на профиль), после предупреждения | 1 профиль из 17, дальше 429 |

**Два способа сбора:**

1. **Полный вход — логин и пароль.** Просмотры приходят пачкой из вкладки
   Reels: один запрос на профиль. Данных больше, нагрузка та же.
   Рекомендуемый способ.
2. **Вход из браузера — без пароля.** Вкладка Reels недоступна, просмотров
   не будет: только лайки и комментарии, тоже один запрос на профиль. Легче
   для аккаунта, но данных меньше.

Есть и третий режим — добирать просмотры по одному запросу на каждый ролик
при входе из браузера. Он **выключен по умолчанию** (`IG_FETCH_VIEWS_ONE_BY_ONE`
в `backend_instagram.py`): именно он и привёл к предупреждению. Если включать,
работает потолок `IG_VIEWS_ONE_BY_ONE_CAP` — не больше 5 таких запросов
на профиль.

Практика: собирать Instagram раз в сутки, охватом «7 роликов», и держать
наготове запасной бёрнер. Предупреждение об этом видно прямо на вкладке
Instagram в окне входа, со значком ⓘ и подробностями.

**Что ещё сделано, чтобы не ловить блокировки:**

- **вход один раз на весь прогон**, а не на каждый аккаунт — 19 входов подряд
  Instagram воспринял бы как атаку;
- **сессия сохраняется в файл** `ig_session_<логин>`, и при следующих запусках
  вход не выполняется вообще: повторные логины — самый заметный для Instagram
  сигнал. Файл равнозначен паролю, права на него ставятся `600`;
- **пауза 8 секунд между профилями**, причём *перед* запросом, а не после —
  тогда нажатая «Стоп» не заставляет ждать впустую;
- потолки: 300 постов и 120 секунд на профиль, чтобы сбор не подвисал.

Из-за пауз Instagram собирается заметно дольше остальных: 19 профилей это
около трёх минут против 30 секунд у YouTube. Это плата за то, чтобы бёрнер
жил долго.

**Про просмотры.** У видео и рилсов счётчик есть, у **фотографий его нет
в принципе** — такие посты дают лайки и комментарии, но ноль просмотров. Это
устройство Instagram, а не ошибка сбора; в тех.журнал пишется, сколько постов
оказалось без счётчика. Из двух доступных чисел берётся `video_play_count`
(«проигрывания») — оно ближе к тому, что Instagram показывает в интерфейсе,
и только если его нет, берётся `video_view_count`.

**Понятные причины отказа:** 429 с просьбой подождать, запрос подтверждения
личности (checkpoint) с объяснением что делать, двухфакторная проверка,
неверный пароль, закрытый профиль, несуществующий профиль, устаревшая сессия.

## Дневной прирост: почему он считается вычитанием

Это не упрощение, а единственный доступный способ. Публичный API отдаёт по
ролику ровно четыре поля:

```
{"viewCount": "29471", "likeCount": "306", "favoriteCount": "0", "commentCount": "0"}
```

Это счётчики **за всё время жизни ролика**. Разбивки по дням в публичном API
нет вообще. Посуточная динамика есть только в YouTube **Analytics** API, а он
требует OAuth-входа в Google-аккаунт владельца канала — то есть связал бы все
20 рабочих аккаунтов в одну систему. Правило изоляции важнее, поэтому этот
путь закрыт сознательно.

Значит, прирост считаем сами: после каждого сбора приложение сохраняет снимок
в `history.json`, а при следующем сборе вычитает из сегодняшних чисел
вчерашние. В таблице это выглядит как `👁 4.7K +239`, в логе — как
`(+239 просмотров за сутки)`. Ровно тот же формат, что в вашей таблице
«Продакшн»: `2611 (+239)`.

Правила, чтобы числа не врали:

- База для сравнения — последний замер **за предыдущий день**. Если сегодня
  собирали уже дважды, второй раз сравнится с первым, и подпись честно
  скажет «с 14:20 сегодня».
- Сравниваются только замеры с **одинаковым охватом** — вычитать «7 роликов»
  из «всей истории» бессмысленно, и приложение этого не делает.
- Аккаунты, которые не собрались, в снимок не попадают: иначе завтра прирост
  считался бы от несуществующего нуля и получился бы огромным.
- Прирост `+0` не показывается — иначе таблица зарябила бы нулями.

`history.json` лежит рядом с приложением, секретов в нём нет — только названия
аккаунтов и числа. Хранится до 500 замеров (больше года ежедневного сбора).

## Охват сбора

Выпадающий список рядом с кнопкой «Собрать метрики»: **вся история**,
**7 роликов**, **30 роликов**, **7 дней**, **30 дней**. Выбор запоминается
между запусками.

Честный замер на ваших 19 каналах — охват сейчас **не экономит ничего**:

| Охват | Учтено роликов | Юнитов | Время |
|---|---|---|---|
| Вся история | 365 | 52 | 23,8 с |
| 7 роликов | 119 | 52 | 24,3 с |
| 7 дней | 112 | 51 | 23,3 с |

Причина: у каждого канала ~21 ролик, а это одна страница по 50 — значит
одни и те же три запроса при любом охвате. Настройка начинает работать,
когда канал перевалит за 50 роликов. Замер на большом канале (526 роликов):

| Охват | Юнитов | Время |
|---|---|---|
| Вся история | 23 | 11,0 с |
| 7 дней | 3 | 1,5 с |

Так работает потому, что `playlistItems` отдаёт дату публикации вместе со
списком роликов, а плейлист отсортирован от свежих к старым — чтение
обрывается на первом же старом ролике, и статистика по остальным вообще
не запрашивается.

**Важная оговорка.** «7 дней» — это НЕ «просмотры за 7 дней», а сумма
просмотров у роликов, вышедших за 7 дней (у каждого — за всё время его
жизни). Это метрика «как заходят свежие публикации». На вопрос «сколько
прибавили за сутки» отвечает только прирост.

**Понятные причины отказа.** Каждая нештатная ситуация переводится на
человеческий язык, а не показывается как «ошибка»: кончилась дневная квота,
неверный ключ, не включён API в проекте, ключ ограничен по IP, канал не
найден или удалён, нет ссылки в экране «Аккаунты», пропала сеть.

**Для YouTube никаких зависимостей.** Он работает на стандартной библиотеке
Python (`urllib`). Для TikTok нужен yt-dlp — он есть в `requirements.txt`.

## Как запустить

### Двойным щелчком, без терминала

| Файл | Система | Что делает |
|---|---|---|
| **`EasyGrab.app`** | macOS | обычное приложение: двойной щелчок, окно терминала не появляется |
| `EasyGrab.command` | macOS / Linux | то же, но открывает окно терминала рядом — удобно, когда нужно видеть ошибки |
| `EasyGrab.bat` | Windows | двойной щелчок; консоль не показывается (запуск через `pythonw`) |

Все три сами находят папку приложения относительно себя — папку можно
переносить куда угодно, пути внутри не зашиты. И все три предпочитают
`venv` рядом с приложением, а системный Python берут только если своего нет.

Если macOS откажется открывать `.command` («не удалось проверить
разработчика») — кликните по нему правой кнопкой, выберите **Открыть**,
затем **Открыть** ещё раз. Это нужно один раз.

### Из терминала (как раньше)

### Windows

```
pip install -r requirements.txt
python main.py
```

Python 3.10+ с сайта python.org уже включает Tkinter — отдельно ставить не нужно.

### macOS (в том числе Apple Silicon — M1/M2/M3)

Код тот же самый, ничего пересобирать под ARM не нужно — Python и
CustomTkinter кроссплатформенны сами по себе. Шрифты подбираются
автоматически под ОС (`fonts.py`), так что Windows-специфичных шрифтов
вроде Segoe UI на Mac не будет.

1. Открой Terminal, проверь версию Python: `python3 --version` (нужен 3.10+).
   Если Python не установлен или старый — поставь универсальный
   (universal2) инсталлятор с python.org, он нативно работает на Apple Silicon.
2. Если используешь Python из Homebrew и увидишь ошибку
   `ModuleNotFoundError: No module named 'tkinter'` — доустанови Tk:
   `brew install python-tk@3.12` (номер версии — под твой `python3 --version`).
3. В Terminal перейди в папку проекта и выполни:
   ```
   cd путь/до/папки/easygrab
   pip3 install -r requirements.txt
   python3 main.py
   ```

Я тестировал это приложение в Linux-контейнере (headless, через Xvfb) —
логика и переходы между экранами проверены по-настоящему, но именно на
macOS 15.7 живьём я его не запускал. Если после установки что-то будет
выглядеть не так или вылезет ошибка — пришли текст ошибки, поправлю.

## Что уже работает по-настоящему

- **Окно входа** (`login_window.py`) — три цветные вкладки-платформы,
  данные не теряются при переключении, чекбокс "запомнить" сохраняет
  их в `session.json` рядом с приложением.
- **Экран "Аккаунты"** (`accounts_window.py`) — таблица-редактор с
  добавлением/удалением строк, пагинацией, сохранением в `accounts.json`.
- **Главное окно** (`main_window.py`) — статус-бар из трёх кружков
  (загорается цветом платформы после входа), кнопка "Собрать метрики"
  реально запускает фоновый поток и обновляет таблицу построчно, по
  мере готовности каждого аккаунта — а не всю пачку разом.
- **Экспорт** (`exporters.py`) — кнопка "Экспорт" открывает выпадающее меню
  с выбором формата: Excel (.xlsx), CSV, TXT, PDF. Все четыре сохраняют
  одну и ту же таблицу метрик, просто в разном виде.
- **"Собрать тех.данные"** (`diagnostics.py`) — кнопка над логом собирает
  подробный технический журнал (каждый вызов сбора с длительностью,
  различие между штатной ошибкой и настоящим необработанным исключением
  с полной трассировкой, падения фонового потока сбора) и сохраняет
  всё в один текстовый файл. Логины/пароли/API-ключи в отчёт никогда
  не попадают — только статус "залогинен/нет".

## Как устроен бэкенд

`mock_backend.py` больше не заглушка. Имя файла оставлено прежним намеренно:
`main_window.py` делает `from mock_backend import simulate_collect`, и не
трогать этот импорт — значит не рисковать уже отлаженным интерфейсом.
Теперь это тонкий диспетчер: выбирает площадку и отдаёт результат в нужном
формате. Реальная логика живёт в отдельных файлах по площадке, чтобы один
файл не разросся до тысячи строк на три соцсети:

| Файл | Что делает |
|---|---|
| `mock_backend.py` | диспетчер: площадка → нужный сборщик |
| `backend_youtube.py` | YouTube Data API v3 (готово) |
| `history.py` | снимки замеров и расчёт дневного прироста |
| `backend_tiktok.py` | TikTok через yt-dlp (готово) |
| `backend_instagram.py` | Instagram через instaloader (готово) |
| `selftest_youtube.py` | самопроверка YouTube без интерфейса (87 проверок) |
| `selftest_tiktok.py` | самопроверка TikTok без интерфейса (56 проверок) |
| `selftest_instagram.py` | самопроверка Instagram без интерфейса и без аккаунта (44 проверки) |

Контракт, от которого зависит вся отрисовка статусов, живое обновление
таблицы и экспорт (**менять нельзя**):

```python
{"ok": True, "views": 128400, "likes": 6200, "comments": 340}   # успех
{"ok": False, "error": "текст причины"}                          # неудача
```

Исключение тоже допустимо: `main_window.py` поймает его и запишет в
технический журнал с полной трассировкой. Поэтому внутри сборщиков
исключения не глотаются молча — предсказуемые ситуации возвращаются как
`{"ok": False, ...}`, а настоящие сбои летят наружу.

## Итог после сбора

По завершении сбора всплывает окно с ответом на главный вопрос — сколько
прибавили за сутки:

```
        Сбор метрик завершён
        Прирост за сутки

  •  YouTube      👁 +300   ❤ +10   💬 +1
  •  Instagram    не собиралось
  •  TikTok       👁 +1 195  ❤ +45   💬 0
     ────────────────────
     Всего        👁 +1 495  ❤ +55   💬 +1

        [ ОК ]      [ Собрать метрики ]
```

Цифры берутся из тех же дельт, что нарисованы в ячейках таблицы, — окно
и таблица не могут разойтись, потому что ничего не пересчитывается второй раз.

**Размер окна подстраивается под содержимое.** Он не задан числом: строки
разложены по `grid`, каждая колонка берёт ровно столько ширины, сколько просит
самое длинное значение в ней, а окно подгоняется под результат.

| Что в окне | Размер |
|---|---|
| обычные числа (сотни–тысячи) | 306×293 |
| сотни тысяч | 367×293 |
| миллионы | 427×293 |

Нижняя граница — ширина ряда кнопок (258 px плюс поля): у́же окно быть не может,
иначе «ОК» и «Собрать метрики» наехали бы друг на друга.

Площадки, по которым не было входа, помечены «не собиралось». В самый первый
замер сравнивать не с чем, и окно так и пишет вместо того, чтобы показать нули.

Кнопка **«Экспорт»** открывает то же самое меню выгрузки, что и в главном окне
(копировать в буфер, xlsx, csv, txt, pdf): цифры перед глазами — и сразу можно
унести их в таблицу. Меню одно на два окна, рассинхронизироваться нечему.

## Анимация

Tkinter не умеет анимаций сам по себе, поэтому взято только то, что работает
надёжно и не мешает:

- **Плавное появление окон** (170 мс). Все диалоги проявляются, а не выскакивают.
  Работает через прозрачность окна; если система её не поддерживает, окно просто
  появится сразу — анимация здесь украшение, а не механика.
- **Полоса хода сбора** под панелью кнопок плюс счётчик «Собираю: 12 из 20»
  вместо даты последнего сбора. Место под полосу занято всегда, поэтому при
  старте сбора таблица не дёргается вниз; в покое это просто разделительная
  линия.
- **Кнопка «Экспорт» загорается**, когда появляется что выгружать. Пока ни один
  аккаунт не собран, выгружать нечего — кнопка нейтральная и не зовёт нажать.
  С первым результатом плавно переходит в акцентный цвет за 300 мс.
- **Подсветка ячейки**, в которую пришёл результат: загорается цветом площадки
  и за 420 мс гаснет до обычного. При сборе 20 аккаунтов строки заполняются
  вразнобой, и без подсветки трудно заметить, куда именно пришло число.

Всё это идёт через `after()` — то есть в главном потоке между событиями,
интерфейс во время анимаций остаётся отзывчивым. Анимации живут
в `ui_utils.py` рядом с расчётом высоты окон.

## Экран «Аккаунты»

**«Отмена» и «Сохранить» закрывают окно.** Раньше «Отмена» только откатывала
правки, а окно оставалось — выйти можно было лишь крестиком. Теперь «Отмена»
отменяет и закрывает, «Сохранить» сохраняет, показывает галочку и закрывает
через 0,7 секунды.

**Ссылки показываются с конца, а не с начала.** Начало у всех строк одинаковое
(`https://www.youtube.com/`) и на экране было видно только его — а различает
аккаунты как раз хвост с юзернеймом. Теперь поле прокручено вправо: видно
`.com/@trappedunderwater`. Текст не меняется, это прокрутка внутри поля —
клик и правка работают как обычно.

**Колонки со ссылками одинаковой ширины.** Раньше у TikTok был вес 2 против 3
у YouTube и Instagram, и на окне 890 px ему доставалось 133 px против 200 —
отсюда и нехватка места. Замерено, что нужно: название 63 px, тематика до 135,
хвосты ссылок 197–231. Веса стали 2 / 3 / 4 / 4 / 4.

**Высота подстраивается под «показывать по»** — и в главном окне, и здесь.
Окно разворачивается так, чтобы выбранное число строк поместилось целиком:

| Показывать по | Главное окно | «Аккаунты» |
|---|---|---|
| 5 | 512 — 5 из 5 | 420 — 5 из 5 |
| 10 | **672 — 10 из 10** | **540 — 10 из 10** |
| 20 | 816 — 14 из 20, дальше прокрутка | 816 — 18 из 20, дальше прокрутка |

Главному окну нужно больше высоты при том же числе строк: у него обвязка
348 px против 216 — из-за лога внизу.

Если экрана не хватает, окно разворачивается на доступную высоту, а остаток
листается прокруткой — она никуда не девается. Высота пересчитывается при смене
«показывать по», но **не** при перелистывании страниц: прыгающее окно на каждом
«>» раздражало бы.

Все размеры измеряются, а не зашиты числами: высота строки и обвязки зависит
от системного шрифта, а он на macOS и Windows разный. Расчёт общий для обоих
окон — `ui_utils.fit_window_height()`.

## Панель кнопок

Слева направо: кружки входа **YT / IG / TT** → **Собрать метрики** → **охват**
→ **Аккаунты**, и отдельно у правого края — **Экспорт**. Поля слева и справа
одинаковые (20 px) на любой ширине окна.

- **Собрать метрики** во время сбора превращается в красную **Стоп**. Нажатие
  останавливает сбор после текущего аккаунта — обрывать уже начатый запрос
  нечем, зато ждать остаётся секунду-две, а не весь прогон. Собранное
  сохраняется в историю, недособранные ячейки возвращаются в «—», а не
  зависают в «⏳».
- **Экспорт** первым пунктом предлагает **«Копировать в буфер обмена»** —
  таблица кладётся с разделителем-табуляцией и вставляется прямо в Google
  Таблицы по колонкам, без «Мастера импорта». Ниже — файлы: xlsx, csv, txt, pdf.

Минимальная ширина окна — 720 px: при 700 кнопки «Аккаунты» и «Экспорт»
смыкаются вплотную.

```

```

Прогоняет 102 проверки на подставных ответах API — разбор всех форм ссылок,
сложение статистики батчами по 50, потолок роликов, скрытые лайки, повторы
при обрыве сети, каждую разновидность ошибки, все режимы охвата, расчёт

С настоящим ключом — живая проверка (потратит несколько юнитов квоты):


## Что починили в этот раз (найдены точные причины, не "на глаз")

**Огромный пустой зазор в главном окне.** Причина — не magic-скейлинг macOS, а конкретная строчка кода: пустой "распорка"-фрейм (нужен, чтобы растолкать кнопки по краям ряда) создавался без явно заданной высоты, а `CTkFrame` в CustomTkinter по умолчанию имеет высоту 200px, если её не задать явно и внутри фрейма нет других виджетов, откуда её можно было бы вывести автоматически. Из-за этого весь ряд кнопок "раздувался" до 200px вместо реальных ~34px. Воспроизвёл баг на изолированном примере, поправил (`height=1` на этой распорке) и заново измерил — ряд кнопок теперь ровно 34px, а освободившееся место ушло в таблицу, как и просили.

**Пароль в окне входа не помещался.** Раньше поле с логином+паролем для Instagram/TikTok позиционировалось через `place()` с процентным смещением внутри блока фиксированной высоты — и при реальном замере оказалось, что смещение "чуть выше центра", о котором просили раньше, оставляло меньше места, чем нужно двум полям с подписями (128px контента против ~80px оставшегося места). Пароль физически вылезал за нижнюю границу блока и перекрывался чекбоксом/кнопкой ниже. Увеличил блок под поля и заменил хрупкое процентное позиционирование на `pack(expand=True)` — стандартный и надёжный способ Tkinter центрировать содержимое переменной высоты внутри области фиксированного размера без риска обрезания. Проверил числами (абсолютные координаты на экране) — поле пароля теперь целиком внутри отведённой области на всех трёх вкладках.

### Из прошлой итерации (тема оформления и выравнивание колонок)

- **Добавлена кнопка переключения темы** (☀/☽ в правом верхнем углу главного окна) — по умолчанию тёмная, как в веб-макетах. Переключение мгновенно перекрашивает все открытые окна (это встроенное поведение CustomTkinter).
- **Исправлена причина "плывущего" интерфейса.** Раньше ширины колонок/вкладок задавались фиксированными пикселями, подобранными на Linux-шрифтах — на macOS системный шрифт шире, поэтому третья вкладка ("TikTok") в окне входа сжималась до нечитаемого вида, а колонки таблицы съезжали. Теперь и вкладки входа, и колонки обеих таблиц — либо жёсткой одинаковой ширины (вкладки), либо синхронизированы через `grid`-механизм Tkinter с общим "uniform"-тегом (колонки таблиц) — ширины гарантированно совпадают независимо от шрифта конкретной ОС.
- **Главное окно теперь реально тянется** — таблица растягивается вместе с окном (раньше у неё была зафиксированная высота, из-за которой при увеличении окна просто появлялось пустое пространство снизу).
- Все "нейтральные" (неактивные) цвета вынесены в `theme.py` парами (светлый/тёмный), а не одиночными строками — поэтому в тёмном режиме элементы не выглядят как случайно забытые светлые пятна.

**Заметка по скорости сбора:** демо-заглушка (`mock_backend.py`) специально имитирует сетевую задержку 0.4–1.6 сек на каждый запрос, а обрабатывает аккаунты по одному последовательно — на 20 аккаунтов и одну залогиненную платформу это ~15–20 секунд, на все три платформы может доходить до минуты. Кнопка "Собираю…" в это время неактивна — это нормально, не зависание. Когда подключите настоящий бэкенд, имеет смысл рассмотреть параллельную обработку (пул потоков) вместо последовательной, если реальные запросы будут такими же по времени.

## Известные упрощения этого каркаса (сделано осознанно, для скорости)

- Иконки платформ в кружках статус-бара и в шапке таблицы — текстовые
  сокращения "YT"/"IG"/"TT", а не полноценные иконки-логотипы: в
  вебмакетах использовался шрифт иконок Tabler, которого нет из коробки
  в нативном Tkinter. При желании — замени `CTkLabel`/`CTkButton` с
  текстом на `CTkImage` с PNG-иконками платформ, остальной код трогать
  не придётся.
- Тултипы (значки ⓘ) реализованы простым самодельным классом
  (`tooltip.py`) через `Toplevel`, а не системными средствами —
  для десктоп-приложения этого достаточно.
- Шрифты подбираются по ОС автоматически (`fonts.py`: Segoe UI/Consolas
  на Windows, Helvetica/Menlo на macOS) — если понадобится другой шрифт,
  меняется в одном месте.
